# LuckPay 国际版移动端设计规范

> 适用项目：`luckpay_uniapp/`  
> 适用角色：金主端、代理端  
> 设计基准：Figma `750 × 1623px`，uni-app 优先使用对应数值的 `rpx`  
> Figma：[LuckPay Mobile International](https://www.figma.com/design/3vF79bc26sQ2wNIz2XSiPG)

## 1. 设计目标

- **可信**：资金、订单、银行卡、押金等核心信息必须稳定、清晰、可核对。
- **高效**：高频任务在两次点击内到达，关键状态无需进入详情即可识别。
- **一致**：金主端与代理端共用视觉语言，但业务信息和导航明确区分。
- **国际化**：适配多语言、多国家、多币种及不同长度的姓名、银行和金额。
- **可落地**：尺寸遵循固定网格，图标使用 SVG，状态完整，可直接映射为组件。

## 2. 产品与角色原则

### 2.1 金主端

- 一个金主账号固定一个国家和一个币种。
- 首页只显示当前币种，不提供币种切换。
- 金主可以管理同国家、同币种下的多张收款卡。
- 实际进入代收卡池的是“收款卡”，不是金主账号。
- 核心任务：查看可用余额与押金、管理收款卡、处理代收/代付订单、上传凭证、查看资金流水。

### 2.2 代理端

- 一个代理可以经营多个国家和币种。
- 国家/币种通过独立业务环境入口切换；切换后整个页面的数据范围同步变化。
- 核心任务：管理下级金主、审核成员或卡片、查看团队跑量、佣金、订单及异常情况。

### 2.3 角色隔离

- 金主端与代理端必须使用不同首页指标、快捷入口和底部导航。
- 不因组件复用而混淆业务名称、权限和信息优先级。
- 页面标题或角色标签应让用户始终知道当前身份和业务环境。

## 3. 设计坐标与响应式规则

### 3.1 基础画板

| 项目 | Figma | uni-app 建议 |
|---|---:|---:|
| 画板宽度 | 750px | 750rpx |
| 标准参考高度 | 1623px | 根据设备自适应 |
| 页面左右安全区 | 48px | 48rpx |
| 最小触控区域 | 88 × 88px | 88 × 88rpx |
| 主按钮高度 | 104px | 104rpx |
| 次要按钮最小高度 | 88px | 88rpx |
| 底部导航参考高度 | 136px | 136rpx + 底部安全区 |

- 设计稿宽度固定为 750；页面高度允许根据内容延伸。
- 不通过缩小字体解决空间不足，应优先换行、扩高或调整信息层级。
- 刘海、状态栏和底部 Home Indicator 使用系统安全区，不写死设备高度。
- 固定底部导航时，正文必须增加对应底部占位，禁止遮挡内容。

### 3.2 网格

- 所有常规尺寸优先使用偶数。
- 间距遵循 `4px` 基础网格，核心间距使用：`8 / 12 / 16 / 24 / 32 / 40 / 48`。
- 同一页面的左右边界、标题起点、卡片起点必须保持一致。
- 同类卡片的标题、金额、状态和操作按钮使用相同对齐线。

## 4. 设计令牌

### 4.1 颜色

| Token | 色值 | 用途 |
|---|---|---|
| `color-bg-base` | `#0E1116` | 页面主背景 |
| `color-surface-default` | `#171B22` | 卡片、输入框、弹窗 |
| `color-surface-raised` | `#202630` | 次级按钮、选项、悬浮层 |
| `color-border-default` | `#303846` | 常规描边、分割线 |
| `color-text-primary` | `#F5F7FA` | 标题、金额、主要正文 |
| `color-text-secondary` | `#9AA4B2` | 辅助信息、说明、占位符 |
| `color-brand-gold` | `#F0C25C` | 主操作、选中态、角色标识 |
| `color-success` | `#25B979` | 成功、已确认、正常运行 |
| `color-info` | `#4B8FF7` | 处理中、待上传、信息提示 |
| `color-warning` | `#F2A93B` | 待处理、即将超时、提醒 |
| `color-danger` | `#F05D68` | 失败、拒绝、冻结、危险操作 |

颜色使用规则：

- 品牌金只用于主按钮、选中态、关键金额和角色标签，不作为大面积装饰色。
- 状态不能只依赖颜色表达，必须同时有文字或图标。
- 资金类主数字优先使用主文字色；只有需要强调收益或状态时使用状态色。
- 正文与背景保持足够对比度，辅助文字不得低于可阅读阈值。

### 4.2 字体

- 首选字体：`Noto Sans SC`。
- 代码回退：系统无衬线字体；数字应启用等宽数字特性（如环境支持）。
- 禁止使用小数形式的字号和行高。

| 层级 | 字号/字重 | 建议行高 | 用途 |
|---|---:|---:|---|
| 大金额 | 54 Bold | 68 | 余额、核心金额 |
| 页面标题 | 44 Bold | 58 | 一级页面标题 |
| 区块标题 | 36 Bold | 48 | 今日概览、待处理等 |
| 正文重点 | 30 Medium | 42 | 卡片标题、按钮文字 |
| 正文 | 28 Regular | 40 | 表单、列表正文、底部导航 |
| 辅助信息 | 24 Regular | 36 | 状态说明、时间、ID |
| 最小标注 | 20 Regular | 30 | 非关键注释、单位 |

- 金额符号、整数、小数和单位的基线要统一。
- 大金额允许缩小一级，但不得小于正文重点字号；优先使用千分位和合理换行。
- 底部导航文字统一使用 28，不允许各页面单独调整。

### 4.3 圆角与描边

| 场景 | 圆角 |
|---|---:|
| 标签、小控件 | 16 |
| 输入框、小卡片 | 24 |
| 主卡片、弹窗 | 32 |
| 胶囊按钮、状态标签 | 999 |

- 常规描边为 2px；重点边框可使用品牌色，但不额外加粗。
- 不使用无意义的多层阴影。层级优先通过背景、描边和间距表达。

## 5. 图标规范

- 生产图标必须为可编辑 SVG/Vector，不使用 emoji、文字字符或多套图标库混用。
- 常规图标视觉框为 `40 × 40`，描边为 `2px`，使用圆角端点和圆角连接。
- 导航图标、功能图标和状态图标分别保持一致的视觉重量。
- 图标与文字按照视觉中心对齐；不能只依据素材原始边界对齐。
- 箭头、密码显示、返回、关闭、通知等系统图标必须在所有页面复用同一资产。
- 图标必须具有默认、选中、禁用和危险状态；选中态可使用品牌金。

## 6. 页面布局

### 6.1 页面结构

推荐顺序：

1. 系统安全区
2. 页面头部/业务环境
3. 核心信息或主要任务
4. 次级数据与列表
5. 底部操作或底部导航

- 首屏只突出一个主要目标。
- 页面标题与首个内容区间距固定，不因页面内容临时变化。
- 同一信息不要同时出现在顶部、卡片和底部导航中。

### 6.2 卡片

- 卡片内边距默认 32，紧凑卡片可用 24。
- 卡片内容间距优先使用 16/24/32。
- 卡片标题、状态、金额、说明和操作必须形成明确层级。
- 可点击卡片需要提供箭头、按压反馈或明确按钮，不能依赖用户猜测。

### 6.3 底部导航

- 金主端和代理端分别维护独立菜单配置。
- 每项包含统一尺寸的图标和 28px 文字。
- 图标中心、文字基线和选中指示线在所有页面完全一致。
- 选中态使用品牌金，未选中态使用次级文字色。
- 页面不得出现与当前角色无关的菜单。

## 7. 核心组件规范

### 7.1 按钮

**主按钮**

- 高度 104，圆角 24 或 32。
- 金色填充、深色文字，用于页面唯一主要动作。
- 状态：默认、按下、加载、禁用、成功、失败。

**次要按钮**

- 高度不低于 88。
- 使用 Raised Surface 或透明底加品牌色描边。
- 同屏多个次要操作需按重要性排序。

**危险操作**

- 使用危险色文字或描边，只有最终确认按钮允许使用危险色填充。
- 删除、退池、冻结、解绑等操作必须二次确认并说明后果。

### 7.2 输入框

- 常规高度建议 104，圆角 24，左右内边距 32。
- 标签位于输入框上方，不依赖 placeholder 作为唯一字段说明。
- 状态：默认、聚焦、已填写、错误、禁用、只读、加载。
- 错误信息紧邻字段展示，说明原因及修正方式。
- 密码显示图标与输入内容垂直居中，触控区域不小于 88 × 88。

### 7.3 下拉与选择器

- 少量选项可使用底部弹层或下拉菜单。
- 币种或国家较多时使用独立选择页面，支持搜索、最近使用和分组。
- 金主首页的币种仅展示，不提供切换。
- 登录线路属于低频配置，应放在顶部设置区域，不抢占登录主流程。

### 7.4 状态标签

- 标签由背景、文字和可选图标组成。
- 使用统一语义：成功=绿、处理中=蓝、提醒=橙、失败/冻结=红。
- 同一业务状态在列表、详情、首页和通知中使用相同名称与颜色。

### 7.5 弹窗与底部弹层

- 普通确认使用居中弹窗；多选项、筛选和长内容使用底部弹层。
- 弹层必须有标题、关闭方式、明确操作和安全区。
- 点击遮罩是否关闭由风险决定；资金确认和验证弹窗不得误触关闭。

### 7.6 空状态与异常状态

每个列表或核心流程至少包含：

- 首次加载
- 骨架屏或加载中
- 空数据
- 网络异常
- 请求失败与重试
- 权限不足
- 账号禁用
- 操作成功
- 超时或订单失败

## 8. 关键业务交互

### 8.1 登录与注册

- 登录页保留语言、币种信息入口和低优先级线路设置。
- 页面主体不展示 Logo，只保留产品名称。
- 不展示版本号和“支持谷歌双验证”等冗余说明。
- 底部固定展示 `金主端 · 国际版`。
- 用户提交登录或注册后，再弹出图形滑动验证；表单内不显示传统验证码字段。
- 注册页面提供“金主账号”和“代理账号”类型；邀请链接指定类型时必须锁定。

### 8.2 邀请注册

- 页面顶部展示上级代理名称、代理 ID、认证状态、申请类型、国家和币种。
- 邀请信息不可由注册人修改。
- 推荐后台分别生成“邀请金主”和“邀请代理”链接或二维码。
- 注册成功后自动归属邀请代理；代理申请可根据规则进入审核状态。
- 无效、过期、停用的邀请链接必须有独立错误页面。

### 8.3 收款卡池

- 收款卡是入池和订单匹配的最小单位。
- 卡片状态至少包括：未入池、审核中、待激活、运行中、已暂停、限流、风控冻结、已退池。
- 入池设置包括单笔限额、每日限额、接单时间、押金模式和自动恢复规则。
- 金主可以暂停自己的卡；风控冻结只能由有权限的代理或平台处理。

### 8.4 资金与押金

- 使用“押金”，不使用“保证金”。
- 首页核心资金卡展示可用余额与剩余押金。
- 操作入口为“押金明细”和“资金明细”。
- 明确显示“需要押金”或“免押金”模式。
- 不同币种禁止合计，跨币种兑换必须作为独立业务并显示汇率与手续费。

### 8.5 订单

- 列表优先展示状态、金额、订单号、时间和剩余处理时间。
- 详情页明确当前步骤、下一步操作和超时后果。
- 上传凭证显示上传进度、失败重试、图片预览和重新上传。
- 关键状态变化需提供页面反馈和消息通知，但避免重复提醒。

## 9. 国际化与本地化

- 所有用户可见文字进入语言包，不在页面中硬编码。
- 验证简体中文、英文以及至少一种文本较长的语言。
- 按钮和标签允许扩展；不能通过过小字号容纳翻译文本。
- 日期、时间、数字、金额、千分位和小数位按地区格式化。
- 货币同时保存 ISO 代码与显示符号；存在歧义时优先展示 ISO 代码。
- 姓名、银行名、代理名、账号等字段支持不同字符集和长度。
- RTL 语言作为后续扩展能力，组件实现时避免强绑定左右方向。

## 10. 动效与反馈

- 动效用于解释状态变化，不作为装饰。
- 普通反馈建议 150–250ms，页面或弹层过渡建议 250–350ms。
- 按钮按下需要轻微明暗或透明度反馈。
- 加载超过约 300ms 时显示加载状态；长请求提供进度或说明。
- 提交操作必须防止重复点击。
- 成功反馈说明结果和下一步；错误反馈说明原因和恢复方式。
- 遵循系统“减少动态效果”设置（平台支持时）。

## 11. 无障碍与可用性

- 触控区域不小于 88 × 88。
- 文字、状态和按钮保持足够对比度。
- 不以颜色作为唯一状态信号。
- 输入框需要可识别标签；图标按钮需要无障碍名称。
- 键盘弹出时，当前字段和主按钮不能被遮挡。
- 金额、订单号等重要信息支持复制，并提供复制成功反馈。
- 破坏性操作必须确认，资金类操作需展示完整金额、币种和目标信息。

## 12. Figma 文件规范

### 12.1 命名

页面命名采用：

```text
模块 / 页面 / 状态 / 角色或币种
```

例如：

```text
Home / Sponsor / Deposit Required / VND
Home / Agent / VND
Register / Agent Referral / Sponsor
Orders / List / Pending
```

### 12.2 页面状态

- 关键交互必须单独保留状态画板，包括下拉、弹窗、加载、失败和成功。
- 新页面优先复用设计变量和已有组件。
- 不复制后留下无意义的图层名称；组件、区域和图标需具备语义名称。
- 交付前检查图层对齐、小数坐标、字体缺失、图片裁切和 SVG 可编辑性。

### 12.3 设计评审顺序

1. 信息架构与业务正确性
2. 操作路径与异常恢复
3. 视觉层级与组件一致性
4. 国际化与极端数据
5. 开发可实现性
6. 截图级视觉检查

## 13. uni-app 落地规则

- 颜色、字号、间距、圆角、层级统一进入主题或 token 文件，禁止页面散落魔法数字。
- 页面头部、金额卡、状态标签、输入框、按钮、底部导航、空状态和验证弹窗应组件化。
- 优先沿用项目现有技术和依赖，不为单个视觉效果引入新的 UI 框架。
- SVG 图标集中管理，并保证颜色和尺寸可由组件属性控制。
- 所有请求按钮实现 loading、disabled 和防重复提交。
- 列表实现加载、空状态、失败重试、分页结束和刷新逻辑。
- 固定元素处理 `safe-area-inset-top` 与 `safe-area-inset-bottom`。
- 业务权限、角色和币种必须由数据状态驱动，禁止只靠前端隐藏入口实现权限控制。

## 15. 变更流程

1. 明确角色、国家、币种和业务状态。
2. 对照现有 Figma 页面和本规范进行设计。
3. 补齐默认、交互、加载、空、错误和成功状态。
4. 设计评审通过后再映射公共组件并开发。
5. 完成构建检查、交互测试和截图对比。
6. 设计规则发生变化时，同步更新本文件、Figma 变量和 `AGENTS.md`。
